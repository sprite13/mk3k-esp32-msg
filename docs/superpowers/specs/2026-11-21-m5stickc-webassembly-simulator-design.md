# Веб-симулятор M5StickC Plus2 на WebAssembly

**Дата:** 2026-11-21
**Статус:** дизайн утверждён
**Связанный проект:** прошивка M5StickC Plus2 для Telegram-уведомлений через Apple ANCS

## 1. Цель

Создать публичный интерактивный веб-симулятор прошивки M5StickC Plus2 по адресу:

- preview: `https://les13.tech/mk3k-esp32-preview`;
- после утверждения: `https://les13.tech/mk3k-esp32`.

Симулятор должен использовать то же платформенно-независимое C-ядро, что и прошивка, собранное Emscripten в WebAssembly. Он нужен для проверки прикладной логики и интерфейса с телефона без физического устройства.

Симулятор не является эмулятором ESP32, BLE или Apple ANCS. Он воспроизводит входные события и состояние приложения, но не доказывает работу Bluetooth, драйверов платы, энергосбережения или реального оборудования.

## 2. Границы первой версии

### Входит в объём

- реалистичная внешняя модель M5StickC Plus2 с экраном 135×240;
- мобильный интерфейс, пригодный для Safari и Chrome;
- ввод `Имя`, `Подзаголовок`, `Текст` и отправка тестового Telegram-уведомления;
- общая C-логика очереди из пяти уведомлений;
- нормализация текста тем же C-кодом, что используется в прошивке;
- навигация A/B, таймер экрана 10 секунд и вытеснение старой записи шестым уведомлением;
- состояния связи с iPhone, заряда батареи и скрытых previews;
- готовые тестовые сценарии;
- опциональный звук буззера после явного включения пользователем;
- статическая публикация без backend и без сохранения пользовательских данных.

### Не входит в объём

- эмуляция ESP32, FreeRTOS, NimBLE, BLE pairing и Apple ANCS;
- подключение браузера к настоящему iPhone или Telegram;
- эмуляция ST7789 на уровне SPI/DMA;
- точная оценка энергопотребления, автономности, ADC и light sleep;
- хранение истории между перезагрузками страницы;
- серверная обработка введённого текста;
- фильтр по выбранным Telegram-контактам.

## 3. Архитектура

### 3.1. Общее C-ядро

Текущий `app_state` переносится из `main/` в новый платформенно-независимый компонент `components/app_core/`. Компонент содержит:

- модель состояния приложения;
- reducer событий;
- очередь последних пяти уведомлений;
- нормализацию текста;
- навигацию к более старому и более новому уведомлению;
- расчёт 10-секундного таймера экрана;
- состояние соединения, заряда и процесса долгого удержания B;
- формирование платформенно-независимой модели экрана.

`app_core` не включает заголовки ESP-IDF и не вызывает FreeRTOS, GPIO, NimBLE, `esp_timer`, `power_manager` или драйвер дисплея. Текущее время передаётся в reducer аргументом в микросекундах. Таймаут экрана, длительность удержания B и время показа результата reset остаются константами чистого ядра. Процент батареи вычисляет платформенный адаптер и передаёт ядру готовым значением 0–100 или признаком «неизвестно».

Аппаратная прошивка продолжает использовать `app_core` через адаптер ESP-IDF. Браузер использует тот же компонент через тонкий WASM ABI. Дублировать reducer или очередь на JavaScript запрещено.

### 3.2. Адаптер ESP-IDF

Существующий `main/app_main.c` остаётся владельцем аппаратных side effects:

- получение событий ANCS;
- чтение кнопок и батареи;
- вызов `board_beep()`;
- управление подсветкой и sleep/wake дисплея;
- удаление BLE bond;
- получение времени из ESP-IDF;
- передача `display_ui_model_t` физическому renderer.

После reducer-вызова адаптер исполняет только явно выставленные ядром эффекты. Это сохраняет поведение прошивки и не переносит аппаратную логику в WASM.

### 3.3. WASM ABI

Emscripten собирает `app_core` и `notification_core` в один модуль. JavaScript работает с непрозрачным экземпляром симулятора через небольшой C API:

- создание и сброс состояния;
- отправка тестового уведомления;
- изменение соединения, заряда и режима previews;
- события press/release кнопок A и B;
- продвижение монотонного времени;
- чтение снимка состояния и модели экрана.

Строки передаются в фиксированные C-буферы существующей модели уведомления. ABI не возвращает указатели с неограниченным lifetime и не требует от JavaScript управлять внутренними C-структурами напрямую. Снимок состояния копируется в фиксированную ABI-структуру, версионированную числовым полем `abi_version`; JavaScript читает только эту копию.

### 3.4. Веб-приложение

Статические файлы размещаются в `simulator/web/`:

- `index.html` — семантическая разметка;
- CSS — mobile-first компоновка и корпус устройства;
- JavaScript — загрузка WASM, привязка элементов управления и Canvas-renderer;
- Canvas — экран 135×240 с масштабированием без изменения логического разрешения;
- Web Audio API — короткий опциональный сигнал буззера.

JavaScript является адаптером ввода/вывода. Источником истины для состояния остаётся WASM.

## 4. Интерфейс

Страница состоит из двух основных областей.

### 4.1. Виртуальное устройство

- корпус и пропорции максимально близки к M5StickC Plus2;
- экран имеет логическое разрешение 135×240 и масштабируется под телефон;
- кнопки A и B нажимаются пальцем и мышью;
- визуально различаются нажатие, удержание и выключенный экран;
- отображаются те же состояния, что предусмотрены прошивкой: уведомление, пустая очередь, нет связи, pairing/reset, ошибка и низкий заряд;
- индикатор позиции показывает текущую запись среди последних пяти.

Экран рисуется по модели, сформированной C-ядром. Canvas-renderer повторяет текущую раскладку, цвета, переносы и fallback-тексты прошивки. Для ASCII, кириллицы и разрешённой пунктуации браузер повторно использует те же bitmap-глифы, что и физический renderer; системные web-шрифты для экрана устройства не применяются.

### 4.2. Панель управления

Поля:

- `Имя` → `Title`;
- `Подзаголовок` → `Subtitle`;
- `Текст` → `Message`.

Управление:

- `Отправить` создаёт тестовое Telegram-уведомление;
- соединение с iPhone: подключён / отключён;
- заряд батареи: 0–100%;
- previews: видимы / скрыты;
- звук: выключен по умолчанию, включается только действием пользователя;
- сброс симуляции очищает RAM-состояние.

Готовые сценарии:

1. обычное сообщение с именем и текстом;
2. только имя;
3. только текст;
4. пустое уведомление;
5. длинный текст с кириллицей и переносами;
6. серия из шести сообщений для проверки вытеснения;
7. потеря и восстановление связи;
8. скрытые previews.

## 5. Поток данных

1. Пользователь вводит данные или выбирает готовый сценарий.
2. JavaScript копирует входные строки в WASM через экспортированный API.
3. `app_core` нормализует уведомление, добавляет его в очередь и включает экран на 10 секунд.
4. Ядро возвращает модель экрана и одноразовые эффекты, например запрос звука.
5. Canvas перерисовывает экран, а Web Audio при разрешённом звуке воспроизводит короткий сигнал.
6. JavaScript каждые 100 мс передаёт ядру монотонное время из `performance.now()`; ядро само решает, когда погасить экран. `requestAnimationFrame` используется только для отрисовки изменившегося кадра.
7. A вызывает переход к более старому уведомлению, B — к более новому; погашенный экран при нажатии снова включается.

Введённые данные не отправляются по сети и не записываются в `localStorage`, cookies или IndexedDB.

## 6. Поведение и ошибки

- Ошибка загрузки `.wasm` показывает понятное сообщение и кнопку повторной загрузки.
- Несовместимый браузер получает текстовое объяснение вместо пустой страницы.
- Слишком длинные строки безопасно обрезаются C-ядром по тем же границам, что и в прошивке.
- Повреждённый UTF-8 не приводит к выходу за границы памяти; применяется существующий нормализатор.
- При выключенных previews тестовое уведомление поступает без содержимого и отображает fallback прошивки.
- При потере связи новые уведомления из панели не принимаются, пока связь не восстановлена; интерфейс явно показывает причину.
- Аудио не запускается автоматически до пользовательского разрешения.
- Симулятор явно маркируется как проверка логики и UI, а не BLE/ANCS-эмулятор.

## 7. Сборка

Сборка должна быть воспроизводимой одной командой из корня репозитория. Она:

1. проверяет закреплённую версию Emscripten;
2. собирает `app_core` и `notification_core` в `.wasm` и JS-loader;
3. собирает статические assets;
4. запускает native и browser-тесты;
5. формирует готовый каталог публикации без зависимости от Node/backend в runtime.

Точная версия Emscripten хранится в репозитории в единственном version-файле, используется локальной сборкой и CI и не допускает плавающих тегов `latest`. Сгенерированные build-файлы не становятся источником истины и не смешиваются с исходниками прошивки.

## 8. Тестирование

### 8.1. Native C

- существующие host-тесты очереди, нормализатора и reducer сохраняются;
- добавляются тесты публичного `app_core` API;
- проверяются таймер экрана, A/B, шестое уведомление, скрытые previews, связь и заряд;
- ASan/UBSan остаются обязательными.

### 8.2. WebAssembly

Одинаковый набор сценариев запускается для native C и WASM. Итоговые снимки состояния должны совпадать по полям, очереди, текущему индексу, экранному состоянию и эффектам.

### 8.3. Браузеры и UI

- Safari на актуальном iPhone;
- Chrome на Android и desktop;
- desktop Safari/Chrome, если доступны;
- touch и mouse ввод;
- portrait layout на узком экране;
- snapshot-проверки ключевых экранов;
- ручная проверка кириллицы, длинного текста, выключения через 10 секунд и серии из шести сообщений.

Аппаратные BLE/ANCS-тесты остаются отдельной матрицей и не считаются пройденными по результатам веб-симулятора.

## 9. Публикация и rollback

- preview публикуется как отдельный статический каталог;
- nginx добавляет только точный маршрут `/mk3k-esp32-preview/` и не меняет существующие upstream;
- все asset URL работают под path prefix, а не только из корня домена;
- для `.wasm` выставляется корректный MIME `application/wasm`;
- preview получает `X-Robots-Tag: noindex, nofollow` и соответствующий meta tag;
- публикация выполняется воспроизводимым deploy-скриптом;
- текущая версия каталога сохраняется для мгновенного rollback;
- после утверждения та же сборка публикуется на `/mk3k-esp32/`.

Перед изменением nginx выполняются проверка конфигурации и резервная копия затрагиваемого site-файла. После публикации проверяются HTTPS, MIME WASM, загрузка с телефона и отсутствие регрессий на существующих маршрутах `les13.tech`.

## 10. Критерии приёмки preview

Preview готов к пользовательской проверке, когда:

1. URL открывается с телефона по HTTPS без установки приложения.
2. WASM загружается с корректным MIME и без backend-запросов.
3. Пользователь может отправить произвольное тестовое уведомление.
4. Кириллица, fallback-тексты и длинные сообщения отображаются корректно.
5. A/B листают последние пять уведомлений в правильном направлении.
6. Шестое уведомление вытесняет самое старое.
7. Экран гаснет через 10 секунд и просыпается от A/B.
8. Состояния связи, батареи и скрытых previews работают.
9. Native C и WASM проходят один набор сценариев с одинаковыми результатами.
10. Страница ничего не сохраняет и не отправляет введённый текст.
11. Существующие маршруты `les13.tech` продолжают работать.
12. Пользователь подтверждает внешний вид preview перед публикацией на `/mk3k-esp32`.

## 11. Структура файлов

Планируемая структура:

```text
components/
  app_core/
  notification_core/
main/
  app_main.c
simulator/
  wasm/
    simulator_api.c
    simulator_api.h
    CMakeLists.txt
  web/
    index.html
    src/
    styles/
    assets/
    tests/
scripts/
  build-web-simulator.sh
  deploy-web-simulator.sh
docs/
  superpowers/specs/
```

Точные имена JavaScript-файлов и инструмента тестирования выбираются в плане реализации. Архитектурное требование неизменно: бизнес-состояние принадлежит C/WASM, браузер отвечает за ввод, Canvas и звук.
